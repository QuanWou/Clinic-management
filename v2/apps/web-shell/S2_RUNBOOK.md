# S2 Reception checkpoint

Open `/workspace?view=reception` in the existing green/white shell. Workspace identifies one clinic from canonical owner/manager/reception membership; if multiple clinics are authorized, use its assigned link with `clinicId`. Branch is a reception location filter within that clinic. The form uses live staff login/current membership/directory APIs, never the synthetic owner identity shown by other shell demos.

## Local setup

Vite dev proxy adds `/s1/identity`→8093, `/s1/clinic`→8092, `/s1/doctor`→8094 and `/s1/encounter`→8101 alongside S1 routes. Patient runs at 8098 and Appointment at 8099. Production must configure gateway routes or `VITE_IDENTITY_V2_URL`, `VITE_CLINIC_V2_URL`, `VITE_DOCTOR_V2_URL`, `VITE_PATIENT_V2_URL`, `VITE_ENCOUNTER_V2_URL` and `VITE_AUTH_URL`; Vite preview supplies no proxy.

All services require their database URL, runtime login/password and separate migration credentials. Encounter uses `ENCOUNTER_V2_DB_*`, `ENCOUNTER_V2_MIGRATION_DB_USER/PASSWORD`, `ENCOUNTER_V2_IAM_URL`, `ENCOUNTER_V2_IAM_SERVICE_SECRET`, `ENCOUNTER_V2_CLINIC_URL`, `ENCOUNTER_V2_CLINIC_SERVICE_SECRET`, `ENCOUNTER_V2_SERVICE_SECRET`. Configure `ENCOUNTER_PATIENT_URL`, `ENCOUNTER_DOCTOR_URL`, `ENCOUNTER_APPOINTMENT_URL` if defaults differ. Ports can be changed with the service's `*_V2_PORT`.

Configure Encounter's source/audit signing key consistently as `PATIENT_SECURITY_ENCOUNTER_SECRET`, `DOCTOR_SECURITY_ENCOUNTER_SECRET`, `APPOINTMENT_SECURITY_ENCOUNTER_SECRET`, `AUDIT_SECURITY_ENCOUNTER_SECRET`. Clinic verifies Encounter's separate Clinic-read key through `CLINIC_SECURITY_ENCOUNTER_SERVICE_SECRET`. Patient reception is opt-in: `PATIENT_V2_RECEPTION_ENABLED=true`, `PATIENT_V2_IDENTITY_URL`, `PATIENT_V2_IAM_SERVICE_SECRET`, `PATIENT_V2_CLINIC_URL`, `PATIENT_V2_CLINIC_SERVICE_SECRET`; Clinic verifies this caller using `CLINIC_SECURITY_PATIENT_SERVICE_SECRET`.

IAM configuration lives in canonical `identity-service`: `IAM_V2_WORKLOAD_INBOUND_SECRET`, its allowed workload issuer list including Patient and Encounter, real legacy identity URL and its existing JWT/Clinic keys. Each caller's IAM secret must match the configured IAM verification key. Current IAM uses a common inbound HMAC key plus issuer/scope checks; this checkpoint does not establish independently isolated per-issuer IAM keys. Restrict workload keys and internal endpoints during deployment. Never reuse the test fixture's known synthetic keys for real traffic.

Enable `ENCOUNTER_RELAY_ENABLED=true`, `ENCOUNTER_RELAY_AUDIT_URL`, and Appointment's existing Notification/Audit relays. Configure Appointment↔Patient booking key and URL so patient-recipient lookup works. Notification is in-app only; missing/unresolvable patient account is explicit MANUAL_CONTACT_REQUIRED.

The exact complete loopback service wiring is demonstrated by `v2/scripts/verify-s2-reception-flow.ps1`. It is a disposable verification harness, not a production launcher.

## Reception actions and recovery

Select the authorized location, then explicitly compare and select a suggested clinic-local patient or create a provisional profile. Sharing phone/name never performs a merge. Review needs evidence reference/reason; it does not create a web-account link.

Choose active doctor and service point. Walk-in creates a visit without inventing an appointment. An ambiguous response freezes the attempted patient/doctor/point/reason and exposes retry of the same key. A confirmed arrival is retained even if queue refresh fails. A distinct arrival starts with **Bắt đầu lượt walk-in mới** after confirmation, then explicit patient selection again. Check-in of an appointment validates its patient/date/source and can resume ARRIVAL_PENDING after a lost remote acknowledgement.

Tokens stay in component memory. sessionStorage holds operation UUID/time indexed by payload digest for up to 24h; no plaintext patient/contact/token is stored. Reload requires sign-in. Choose the same authorized location and reception day, then use **Tra cứu lượt đã gửi** to read this staff actor's server receipts. Confirm the completed outcome or resume ARRIVAL_PENDING with a recovery reason; source recovery uses the original patient/booking/point, without reconstructing browser patient inputs. This endpoint is receipt-owner only, bounded to 100 visits/day. Supervisor handoff and reconciliation after prolonged source failure remain unfinished. A new-walk-in action adds a distinct opaque intent so a recovered old payload does not silently replay as a new arrival.

Queue call/skip/transfer are version checked and require reason; transfer is within the branch. Conflict requires refresh before retry. Doctor worklist/start exists in the backend; a complete doctor clinical UI is still S3 work.

S3 continuation adds `/workspace?view=doctor`: sign in with a canonical DOCTOR membership, select the granted location, choose an assigned visit and supply a reason. Start requires a called current-day ticket. Await-results retires the serving ticket and retains the same encounter. Return selects a service point and rejoins its queue; reception must call before doctor resumes. The worklist includes awaiting encounters from earlier days. Unknown responses expose retry of the frozen key/body and reload; 4xx requires a fresh worklist. No clinical completion/sign/release occurs here. See [care contract](../../contracts/s3-care.md) and `pwsh -NoProfile -File v2/scripts/verify-s3-local.ps1` for the separate 109-test checkpoint.

Late/no-show/doctor-absence reporting records OPEN exceptions. No-show does not fabricate slot/financial reversal. Under **Báo bác sĩ vắng theo khoảng lịch**, manager reports an interval (Vietnam time; maximum 31 days per report). Doctor source windows block overlapping new availability/hold/confirmation. Load saved intervals after uncertain outcome/reload. The report preserves existing bookings; press **Ghi ngoại lệ các lịch bị ảnh hưởng** for each batch of at most 10, inspect retry/remaining counts and continue until affected bookings are processed. Idempotent source linkage prevents duplicate exceptions across managers. A racing rebooking is rechecked in the locked Appointment transaction.

This is explicit staff-driven propagation; interval creation does not imply patient notification or completed bulk processing. MANUAL_CONTACT_REQUIRED needs follow-up; IN_APP is consumer delivery, not read receipt. Background propagation, amendment/cancel of an absence, exception resolution UI and approved rebooking/refund remain unfinished. Doctor reason/actor stay out of public windows/events. Source interval history is local Doctor data; a dedicated external Doctor absence audit consumer is not implemented by this checkpoint.

## Verification

From repo root run `pwsh -NoProfile -File v2/scripts/verify-s2-local.ps1 -KeepSandbox` (PowerShell 7). It creates its own loopback PG instance/UUID directory and eight fresh databases, uses real migrations/runtime logins, requires zero skipped tests, packages services, exercises eight real service HTTP endpoints and stops its own children/PostgreSQL. KeepSandbox records `RETAINED_BY_CONFIGURATION` and retains the directory. The current run uses this mode after automatic approval review blocked cleanup of a prior failed-start sandbox; those denied targets are not retried. Legacy current-user/token issuing is synthetic; V2 Identity/IAM is real. Confirmed appointment inputs are seeded; the separate S1 flow covers public booking creation. This does not claim complete authentication or clinical/financial E2E.

From this app directory: `npm test`, `npm run build`, `npm run test:browser`. Browser tests use HTTP fixtures and record 1440px/375px layouts in P05-S2 evidence; they do not substitute for backend integration. Manual accessibility and real deployed user journey remain downstream work.
