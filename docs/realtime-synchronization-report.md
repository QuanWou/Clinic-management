# System realtime synchronization audit and implementation

Audit date: 2026-10-07. The pre-implementation inventory is [realtime-inventory.md](realtime-inventory.md). This report describes the actual React application and five Java core services in this checkout. Existing unrelated working-tree changes were preserved.

Operational consumers now use scoped SSE invalidation followed by authorized REST reads. Public booking uses bounded availability revalidation and authoritative hold/confirmation checks. Configuration uses clean-form focus recovery; historical data and explicit reconciliation commands retain deliberate user control.

## 1–5. Applications and original refresh dependencies

1. **Applications audited:** one React/Vite application, comprising PublicShell, the Patient portal, WorkspaceShell (Doctor, Lab, Reception, Cashier, Admin, configuration and platform review), and the capability-authorized CustomerPaymentDisplay. There are no separate frontend applications or a separate prescription workflow in this repository. Released clinical document content and reviewed results come from the existing patient record API; no prescription subsystem was invented.
2. **Infrastructure discovered:** authenticated streaming `fetch`, Spring SSE, PostgreSQL LISTEN/NOTIFY, transactional domain outboxes, a streaming gateway, and separate clinic/doctor/catalog publication projections. Existing branch realtime infrastructure supported Appointment, Encounter and Billing for Reception/Cashier consumers. Reception's present queue screen consumes Appointment/Encounter; it has no payment-detail column requiring a Billing subscription. The frontend uses component state, without TanStack Query, SWR or RTK Query. The implementation extends this infrastructure rather than adding a second transport stack.
3. **Manual dependencies found:** Doctor worklists, Medical/Lab reads, Patient appointments/history/bills/follow-up, Admin monitoring, configuration sources, operational recovery tools, cashier intent/notification/charge inspection and the display error flow. Normal data freshness now has a background path. Secondary source refresh controls remain useful for deliberate inspection, historical reports, retrying uncertain commands, choosing another page, reviewing a conflicting draft, or explicitly reconciling a provider. Those buttons no longer constitute the operational synchronization mechanism.
4. **Polling found and changed:** Doctor's unconditional 30-second network polling was replaced with scoped subscriptions. Display's perpetual 2.5-second polling and Patient intent's 5-second polling capped at five minutes were replaced. Cashier's unconditional intent polling was replaced. Remaining network intervals are narrowly mounted: booking eligibility 30 seconds, evaluated booking slots 15 seconds until a hold, active payment intent/display 15 seconds until terminal state, selected charge/notification-delivery inspection 30 seconds, disconnected SSE consumer fallback 30 seconds, and the existing canonical session check 45 seconds. Hidden documents defer reads. One-second hold/intent timers and Reception's 30-second timer only update clocks.
5. **Full reload audit:** CustomerPaymentDisplay's error retry used `location.reload()`; it now retries its authoritative request. No normal synchronization use of `location.reload()`, `window.location.reload()` or `history.go(0)` remains. Session/identity isolation keys are retained. The browser test counts actual document navigation requests separately from React route changes.

## 6–10. Domains, producers and consumers

6. **Realtime domains (A/B):** Appointment status, queue/Encounter lifecycle, Medical orders/results/worklist summaries, patient release, bills/payment intents/receipts, capability payment display, user notifications, operational exceptions and current Admin counters.
7. **Revalidation/static domains (C/D):** public content/biographies, clinic/doctor/catalog/pricing/membership configuration, staff tables, platform review, security settings and explicit historical reports. Active booking is a justified B exception to otherwise C publication data because selection can become obsolete while a customer is deciding.
8. **Wire events:** `ready`, `changed`, and `denied`; authorized streams carry only `refetch`. The domain is determined by the subscribed owner endpoint, not a global `system.changed` message. Existing persisted domain-event names remain unchanged. No medical entity, payment detail, database notification payload, access token or versioned entity is sent in the hint.
9. **Producers:** Appointment row mutations; Encounter transactional outbox insertion; Medical transactional outbox insertion; Billing bill/intent/delivery mutation; Notification inbox/read/preference mutation. PostgreSQL delivers transactional notifications after commit. A rolled-back notification was verified not to arrive. New additive migrations are Appointment V14, Encounter V15, Medical V4, Billing V11 and Notification V3; existing Reception/display migrations remain in place.
10. **Consumers:** owner-specific Doctor/Patient streams, authorized Reception/Admin/Cashier branch streams, the current user's notification stream, and one bill's display capability stream. The complete per-surface matrix below identifies each owner and final strategy.

## 11–17. Correctness, recovery and security

11. **Invalidation:** `useAuthoritativeSync` serializes reads, coalesces hints for 120 ms, retains affected source domains and refetches authorized REST endpoints. Admin domain hints refresh current operational sources without repeatedly loading staff, schedules, prices or historical charts. Focus revalidation also refreshes configuration warnings. REST fetches use `cache: no-store`. There is no client entity cache to mutate from an event.
12. **Reconnect:** initial/reconnected `ready` causes a full relevant authoritative read. The transport detects stalled streams after 45 seconds and retries with 1–30 second backoff. SSE rotates after approximately 55 seconds. Failed REST reads retry independently with 2–30 second backoff, even if no new event arrives. Server LISTEN reconnection advances a readiness epoch so consumers refetch missed changes. Hints are intentionally non-durable; recovery reads provide correctness across event gaps.
13. **Focus/visibility:** focus, online and visible-document transitions schedule recovery. Hidden documents retain pending invalidations. Cleanup removes timers/listeners/subscriptions; duplicate consumers share a connection and the last consumer closes it. On the server, one LISTEN connection is shared per module rather than allocated per browser subscription.
14. **Tenant isolation:** controllers choose channels from authenticated scope. Branch channels include clinic and branch; Doctor channels also include assigned user; Patient channels also include owned patient; Notification channels include current user; display channels include the capability's bill. Hashed channel names are identifiers, not authorization. The existing tenant/RLS and owner REST checks remain authoritative.
15. **Authorization:** checks run before subscribing and again on heartbeat/hint. Clinical reads require the existing Doctor authorization; operational/finance Admin capabilities do not grant access to clinical note streams. Patients must own the requested patient identity. Display tokens retain expiry and bill restrictions. HTTP 401/403 and explicit denial stop that subscription and clear affected state; display 404 is terminal. Dependency outages retry. Initial HTTP security still applies; ASYNC dispatch is permitted so an already-authorized SSE response can complete without an erroneous second authentication failure. Canonical session checks still handle permission/context changes.
16. **Duplicates/order:** hints contain no old state to apply, so delayed or duplicate messages only refetch the latest owner state. One read runs per consumer at a time. Scope and edit-generation guards discard late results after identity/navigation/edit changes, including a read that started before a mutation and finished after it. Payment webhook replay remains idempotent at Billing; one persisted receipt was verified. Badge counts replace authoritative counts, never increment based on delivery count. The unread endpoint counts all unread inbox rows, independently of the latest-50 list limit.
17. **Local edits:** clean server-owned order/result data can update while a medical note remains unsaved. A newer document version is shown for review and automatic saving is disabled until reviewed. Other mutation/result/approval/configuration/exception inputs defer reconciliation; hints remain pending and drain after editing ends. Existing idempotency keys, unknown-result retry payloads and explicit conflict actions are preserved. Loaded Doctor worklist pages and a separately authorized selected encounter are retained to avoid losing an active draft because it moved outside the current page. Admin totals show `—` when a required current branch source is unavailable rather than silently counting it as zero.

## 18–26. Verification results

The real-service test runs against an independent PostgreSQL 17 cluster restored from the project's checksum-verified backup, with five newly built cores, the real gateway and separate Edge browser contexts. Source database credentials/data, the existing main runtime and installed PostgreSQL service were not changed. QA credential/slot preparation and synthetic clinical/payment fixtures are confined to that copy. The configured source database was unavailable, so it was not used as a test target. Remote decorative font requests are blocked in the browser harness because an unavailable external stylesheet can delay application startup; application and owner API traffic are real.

18. **Queue:** Reception check-in invalidates the already-open Doctor worklist. A same-slot competing patient hold is rejected. Queue resume and completion execute through real owner APIs.
19. **Doctor/Reception:** real Doctor call/start commands automatically update Reception to `Đã gọi` / `Đang khám`. Changes also reach the assigned Doctor stream; an unrelated Doctor stream receives no changes.
20. **Lab:** authenticated order/accept/process/result/review commands reach Medical; the already-open Doctor worklist displays `Có kết quả mới`. Unreleased result activity does not emit a Patient hint or appear in the Patient record API. Lab input conflict/uncertain-command behavior and note preservation are also covered by frontend tests. The browser scenario submits Lab commands through the real API; it does not pretend a separate Lab browser operator was tested.
21. **Booking:** competing reservation protection is verified. Admin disables a doctor; the owner booking API removes eligibility and rejects both a new stale hold and confirmation of an existing hold. Unavailable-doctor rejection is HTTP 404 in this API. The already-open public booking form automatically removes the obsolete selection within the 30-second revalidation window. Slot refresh itself uses the 15-second evaluated-selection scope; an exhaustive schedule/absence/catalog/pricing mutation browser matrix was not run.
22. **Patient portal:** the already-open appointment list changes, unreleased records remain withheld, completed/validated records and reviewed results appear automatically, and the already-open invoice recovers authoritative PAID plus one receipt after browser offline/online.
23. **Payment:** a signed synthetic payOS webhook exercises the production signature verifier and Billing transaction. Cashier balance, Admin financial counters, CustomerPaymentDisplay and reconnected Patient update automatically. Replay creates one receipt. No real payOS request, bank transfer or money movement was performed; QR image network requests are blocked in the test. Other payment/reconciliation operations retain their existing unit coverage, not an unperformed live-bank PASS.
24. **Notification:** the already-open Patient unread badge changes, delivered financial notifications appear for the correct recipient, another patient receives no hint, and persisted read state is verified. Shared inbox frontend tests cover authoritative counts and late identity/read responses.
25. **Admin propagation:** finance counters change without reload; operational/finance subscriptions are authorized; disabling the Doctor reaches already-open public booking and authoritative confirmation. Clean configuration, staff and platform review recovery have frontend coverage; a real multi-admin cross-tab edit/revocation browser matrix was not run.
26. **Multi-session:** Reception, Doctor, Cashier, Admin and Patient remain open simultaneously; Display and Public booking are added as separate pages. The test uses real authentication and a real gateway, checks negative tenant/clinical/other-patient subscription authorization, commit/rollback, recipient scope, delayed hints, payment replay and reconnect readiness. The final run **passed all 27 assertions** at **2026-10-07 15:40:16 UTC+07**, with zero JavaScript errors and one initial document request per monitored browser surface. Reception check-in reached the already-open Doctor view in **424 ms** in this run; this single measurement is not a production latency guarantee. ## 27. Limits and remaining stale-state risks

- C surfaces intentionally revalidate on focus/navigation and preserve edited forms. An uninterrupted open configuration editor may retain its old source until editing finishes and recovery is triggered; owner version/eligibility checks still reject conflicting commands.
- Active public booking can retain options for up to 30 seconds and evaluated slots for up to 15 seconds. Publication projection delay or an owner outage can extend freshness delay. Holding/confirmation always rechecks the owner, so a displayed option is not a booking guarantee. A held booking is not silently discarded while the user is confirming it.
- Historical audit pages, historical Lab inspection and seven-day charts are explicit snapshots. Current counters refresh on hints, while history refreshes with report-date/source inspection. Historical chart aggregation retains the existing partial-source behavior; it is not advertised as realtime financial reconciliation.
- During network/owner failure, the last successful data can remain visible while retrying. Operational status/last-sync indicators and source errors remain relevant; a stream connection alone is not proof a REST read succeeded. Browser focus/offline recovery is verified; actual PostgreSQL server termination/restart and load/soak testing were not performed.
- Notification delivery still depends on the existing durable asynchronous relay. Push starts after the inbox transaction commits; the UI does not assume a delivery succeeded from Billing's payment event alone.
- Existing Lab access is the assigned Doctor model. A separate laboratory role/global lab branch channel was not introduced. Changing that authorization model requires its own explicit domain work.
- Tests with missing external DB/container prerequisites and live payment-provider traffic are unverified. New migrations were exercised by the isolated real cores; they have not been deployed to the user's main runtime.

## Reproduction and evidence

- `npm run build` and `npm test` in `frontend`.
- `mvn -B -ntp -f backend/pom.xml clean test package` using Java 21 and Maven. DB/container suites require their documented prerequisites; absent prerequisites produce skips.
- `scripts/start-realtime-sandbox.ps1` prepares a **fresh**, independent test cluster from `.runtime/main/config.json`'s verified snapshot and copies/builds the backend. It refuses to overwrite a retained cluster. It requires the local PostgreSQL 17 tools, Java/Maven, frontend dependencies, Edge and the private snapshot configuration; it does not fetch or log credentials.
- `node scripts/verify-realtime-system.mjs --sandbox` exercises the running isolated cores/browser. It refuses a non-sandbox database name/port configuration. Run on a day with future scheduled fixture slots. Fixture setup modifies only disposable copied accounts/appointments.
- `scripts/stop-realtime-sandbox.ps1` checks recorded process identity and the resolved cluster path, stops only the owned sandbox, and retains its evidence/snapshot. Runtime credentials and raw configuration remain ignored local files.

Key implementation files: `frontend/src/api/realtime.ts`, `frontend/src/components/useAuthoritativeSync.ts`, `frontend/src/components/NotificationInbox.tsx`, `backend/realtime-lib`, owner realtime controllers/migrations, and the audited consumer components listed in the inventory.
