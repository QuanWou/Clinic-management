## API (all JWT authenticated)

| Route | Permitted role | Behavior |
| --- | --- | --- |
| `POST /api/invoices` `{ "appointmentId": "UUID" }` | `ROLE_ADMIN`, `ROLE_RECEPTIONIST` | Confirm completed appointment, finalized performed services, all lab orders released, effective catalog prices; snapshot every item or fail closed. Never accept client `totalAmount`. |
| `GET /api/invoices/{id}`, `/appointments/{appointmentId}`, `/my`, `/patients/{patientId}` | Established role/ownership checks | Invoice header + item snapshots including unit price, quantity, source ID, catalog price ID, currency. |
| `POST /api/invoices/{id}/cash-payment` `{ "receiptReference": "COUNTER-123" }` | Admin/receptionist | Staff explicitly attests **physical** cash received. Locks invoice, checks verified snapshots, writes unique capture receipt/audit and durable undelivered event intent atomically, transitions `UNPAID` -> `PAID`. |
| `POST /api/invoices/{id}/cash-refund` `{ "refundReference": "REF-123", "reason": "..." }` | Admin only | Attests physical full refund only for an audited cash capture. Retains original capture, appends reversal and actor/time. |
| `PATCH /api/invoices/{id}/cancel` | Admin/receptionist | Only `UNPAID` invoice, actor/timestamp recorded. |
| `GET /api/invoices/{id}/transactions` | Admin/receptionist | Cash ledger. |

`PATCH /api/invoices/{id}/pay` is intentionally REMOVED (test asserts 404). `CARD`, `BANK_TRANSFER`, `INSURANCE`, patient-click, redirect, mock or unsigned webhook never mark `PAID`. A retry with the same invoice and receipt returns existing `PAID` without new transaction or event; a different receipt or reused receipt fails. Database `SELECT FOR UPDATE`, invoice unique appointment, transaction unique external receipt and invoice/type, item unique `(source_type,source_id)` provide concurrency guards. Database locking has **not** been exercised on PostgreSQL yet.

## Actual upstream contracts (separate, NOT merged Task 02/04 worktrees)

- **Appointment** `GET /api/appointments/{id}` (port 8086, authenticated) supplies `id,patientId,doctorId,appointmentDate,status`. Only `COMPLETED` is eligible. This does **not** identify a catalog service or prove it was performed.
- **Performed services (BLOCKER P0)**: Task 03 currently has no authoritative finalized list of `{appointmentId,performedItemId,serviceId,quantity,serviceDate,finalized,revision}`. `PerformedServicesClient` explicitly fails with HTTP 409 rather than assuming that `doctorId`, appointment existence or a client-selected service is a charge. Task 03 has been asked for an actual API. Service-level tests inject a mocked verified source solely to exercise downstream orchestration; this is not evidence of working integration.
- **Lab (BLOCKER P0)** Task 04 port 8087: `GET /api/medical-records/appointments/{appointmentId}/billable-items`, staff JWT, *currently* `ApiResponse.data={appointmentId,items:[{orderId,testCode,quantity,status,billableAt}]}`. All orders including pending are returned; only `RELEASED` with valid `billableAt` may be billed. The current response **does not** prove that new lab orders cannot be added immediately after invoice creation. Billing additionally requires authoritative `finalizedForBilling=true` and nonblank `billableRevision` backed by an immutable freeze contract. These fields do not yet exist in Task 04: their absence fails closed with HTTP 409, including when items is empty. This requirement was dispatched to Task 04. Billing now requires a verified catalog `serviceId` and `performedOn` from each released lab order and checks that `testCode` matches the catalog service. These fields are NOT supplied by the current Task 04 API, so production remains fail-closed. No late-order/adjustment policy has been implemented.
- **Catalog** Task 02 port **8091** (`CATALOG_SERVICE_URL`, default `http://localhost:8091`): `GET /api/catalog/services` (active services), `GET /api/catalog/services/{id}` and `GET /api/catalog/services/{id}/price?on=YYYY-MM-DD`. Responses are `ApiResponse` wrappers; `service` fields `{id,code,name,description,active}`, `price` fields `{id,serviceId,amount,currency,effectiveFrom,effectiveUntil}`. Catalog `price.id` is the price-version ID and validity end is exclusive. `PricingClient` validates active service, IDs, positive precision-bounded VND amount, requested date inside validity period, then snapshots immutable `priceId` per item. Lab pricing uses Task 04's authoritative `serviceId` + `performedOn` through `GET /api/catalog/services/{id}/price?on=...`; it rejects mismatched `testCode` instead of inferring an ID from a name/code. An unavailable/invalid price returns 409, without defaults.

The old `/api/pricing/appointments/{id}/quote` on port 8085 **does not exist** and is no longer called. No fabricated appointment quote is accepted. Headers use the existing authenticated caller's JWT; upstream role and information disclosure must be integration-tested after both services deploy.

## Required cross-service finalization protocol (not deployed)

Task 03 must persist performed service IDs, quantities and dates from authorized clinical/reception workflow, and make `finalized=true,revision` permanent: once finalized, reject additions, edits, deletions and rescheduling that alters chargeability. Task 04 must persist a billing-closure marker for every appointment (including appointments with zero lab orders); its finalization transaction locks the appointment's lab parent/closure row, refuses pending lab orders, and atomically prevents all future create/update/release operations for that appointment. Every lab mutation must acquire the same row lock and reject a closed marker. Only Task 04 may confirm `finalizedForBilling=true` and issue the frozen `billableRevision`. Reject late lab orders after closure; a separate authorized supplemental-encounter/adjustment policy is required before charging subsequent care. A GET returning an empty list or a revision number without this write-side enforcement is NOT sufficient.

Billing requires both immutable finalized source snapshots before requesting Task 02 prices, validates item UUIDs and effective dates, re-reads appointment and both source revisions/item lists immediately before insert and stores revisions with source IDs/price IDs. Its own PostgreSQL unique appointment and `(source_type,source_id)` constraints arbitrate duplicate invoicing. A read/re-read scheme alone is NOT cross-service locking; the P0 remains until Task 03/04 implement and prove the immutable writer-side protocol with real concurrent HTTP tests. Dispatch requests to their owning tasks have been queued; they are not an assertion those tasks executed. `PerformedServicesClient` will not point at an invented endpoint before Task 03 confirms an actual implemented route.

## Monetary persistence and migration

Flyway V1 unchanged. V2 adds cash audit and ledger; reclassifies historical `PAID` rows to `RECONCILIATION_REQUIRED` without creating evidence. V3 quarantines **all** pre-migration `UNPAID` rows (they lack item snapshots, even those with a provisional revision), adds invoice currency and item snapshots. Each item has source type/UUID, service UUID/code/name, actual immutable price UUID, service date, unit price, quantity, line amount, VND and database CHECK/UNIQUE constraints preventing duplicate lab order billing. `catalogRevision=PRICE_IDS_PER_ITEM` indicates that version is tracked individually by `priceId`, **not** a real global catalog revision. Total amount is recalculated server-side from items, bounded to NUMERIC(12,2); cash capture refuses absent or inconsistent snapshots. V5 adds `performed_revision` and `lab_revision` to invoices with a DB constraint requiring both for new `UNPAID` rows; the source values are stored on invoice creation. Billing re-reads the appointment, services and lab snapshot immediately before the DB write and rejects changed revisions or changed items. A second read by itself cannot close a cross-service race: both sources must enforce irreversible finalization/freeze in their own write transactions.

V4 adds `invoice_paid_outbox` with one immutable `INVOICE_PAID` event ID per invoice, written in the **same transaction** as a confirmed cash capture, and status `WAITING_RECIPIENT`. **No publisher is running** and no event has been emitted: patient profile UUID is NOT an identity user UUID. Task 06 requires a verified identity user ID, AMQP exchange `notification.exchange`, routing `notification.business`, persistent outbox + post-commit publisher confirmations. Implement recipient resolution and publisher with Task 03/06 and verify commit/retries before enabling delivery; do not publish before commit or claim notifications are operational.
